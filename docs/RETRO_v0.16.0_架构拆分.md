## 三、关键决策点

### 决策 1：IIFE + window 命名空间 vs ES module

| 维度 | 采纳方案（IIFE+window） | 备选（ES module） |
|------|------------------------|-------------------|
| file:// 兼容 | ✅ 双击 HTML 即可运行 | ❌ CORS 阻止，必须 HTTP 服务 |
| 零构建工具 | ✅ 直接 `<script src>` | ❌ 需处理裸路径导入 |
| 迁移风险 | ✅ 最小改动，只加 IIFE 壳 | ❌ 全量重写 var→const/let，window.xxx→export |
| 加载时序 | ✅ `<script>` 天然顺序 | ❌ `<script type="module">` 默认 defer |

**评价**：正确决策。standalone.html 的核心使用场景是本地双击（file://），这是硬约束。ADR 中"IIFE+window 是 ES module 的超集兼容写法，不是死胡同"的判断也为未来演进留了后路。唯一代价是全局命名空间污染，但 6 个 `window.CONST/ALGO/GONGWEI/RENDER/ARCHIVE/APP` 命名空间在实际场景中冲突概率极低。

### 决策 2：6 模块划分边界

| 模块 | 行数 | 职责 |
|------|------|------|
| constants.js | 857 | 纯数据/常量（零依赖） |
| algorithm.js | 672 | 纯排盘算法（零 DOM） |
| archive.js | 866 | 档案 CRUD |
| gongwei.js | 860 | 宫位 UI 逻辑 |
| render.js | 1513 | 视图渲染 |
| main.js | 873 | 入口/事件/测试 |

**评价**：边界清晰，职责单一。实际产出与 PRD 预估行数高度吻合（最大的偏差在 constants.js：预估 450 行 vs 实际 857 行，几乎翻倍——说明大量常量在单体文件中被低估了）。algorithm.js 实际 672 行低于预估 1000 行，说明算法部分比预期精简。

### 决策 3：加载顺序微调

PRD 原始规划顺序为 `constants → algorithm → gongwei → render → archive → main`，ADR 和实际实现调整为 `constants → algorithm → archive → gongwei → render → main`。理由是 archive.js 只依赖 CONST（弱依赖），不依赖 ALGO，可以提前加载。

**评价**：合理调整。测试师在 QA 报告中也注意到了 UPGRADE_PLAN.md 与 ADR 的不一致问题（问题1），发布前已修正。这说明依赖拓扑分析在跨文档一致性方面仍有改进空间。

### 决策 4：CSS 不拆、不引入构建工具

PRD 明确将 CSS 拆分和构建工具列为"非目标"。

**评价**：务实。744 行 CSS 在当前阶段拆分收益不大（不像 JS 那样有维护瓶颈），构建工具的引入会破坏"改完即刷新"的开发体验。但需注意 CSS 文件也在增长——当 CSS 超过 1000 行或需要主题切换时，应考虑独立拆分。

## 四、遇到的问题和解决方案

### 问题 1：编程师 3 轮停滞（~24 分钟无响应）

**现象**：编程师在执行过程中出现 3 轮长时间无响应。
**影响**：实现阶段耗时被拉长，成为流水线瓶颈。
**根因推测**：
- 任务复杂度——将 5497 行单体文件按精确边界拆分为 6 模块，涉及大量函数迁移和 HTML onclick 改名，认知负荷高
- ADR 虽然给出了逐函数行号清单，但编程师仍需逐段验证、调试
- 可能涉及模型上下文窗口限制——5497 行单体文件接近或超出单次读取上限

**解决方式**：编程师最终自行恢复并完成，产出质量高。

**建议**：
- 对超长文件的拆分任务，考虑"渐进式拆分"策略（如 ADR 回滚方案所述：先拆 2 个模块验证，再拆其余 4 个），降低单次认知负荷
- Leader 可设置更短的停滞超时阈值（如 8 分钟），主动 ping 编程师确认状态

### 问题 2：预估行数与实际偏差（constants.js 翻倍）

**现象**：PRD 预估 constants.js ~450 行，实际 857 行。
**根因**：单体文件中常量散落在多处（L751-L1147 + L1550-L1700），PRD 统计时遗漏了大量运行时也需要的静态数据（农历数据表 LUNAR_INFO、节气表 SOLAR_TERMS、人元司令表 REN_YUAN 等）。
**影响**：无实际影响——只是预估偏差，不影响拆分方案。
**建议**：在 PRD 阶段用脚本自动统计行数（如 grep 关键段），替代人工估算。

### 问题 3：跨文档不一致（UPGRADE_PLAN.md vs ADR）

**现象**：UPGRADE_PLAN.md 规划的加载顺序（gongwei→render→archive）与 ADR 和实际实现（archive→gongwei→render）不一致。
**发现者**：测试师（QA 报告问题1）。
**解决**：发布前更新 UPGRADE_PLAN.md 与 ADR 对齐。
**建议**：这类"规划文档与实际落地不一致"是流水线的常见问题。建议在发布 checklist 中增加"文档一致性检查"专项，或由流程师在复盘时做 diff 对比。

### 问题 4：JS 模块放在根目录而非 js/ 子目录

**现象**：6 个 JS 模块位于项目根目录，而非 UPGRADE_PLAN.md 规划的 `js/` 子目录。
**等级**：测试师评为"🟢 提示"，可接受。
**理由**：ADR 的 `<script src="constants.js">` 就是无路径前缀的——这意味着模块放在根目录是 ADR 的隐含设计，UPGRADE_PLAN.md 的 `js/` 规划才是偏差方。
**建议**：统一文档中的目录描述。

## 五、流程可改进之处

### 1. 缺少阶段时间戳自动采集

当前流水线没有任何机制自动记录每个阶段的开始/结束时间。复盘时只能靠 Git log 倒推，无法精确分析瓶颈。
**建议**：在流水线中增加轻量级埋点——每个 Worker 开始/结束任务时向 Leader 发一条带时间戳的状态消息，Leader 汇总为时间线。

### 2. PRD/ADR 之间存在信息冗余

PRD（323 行）和 ADR（566 行）有大量重叠内容：模块职责描述、依赖关系、行号估算等在两份文档中都出现了。这是"高质量冗余"——它保证了编程师即使只读 ADR 也能开工，但也意味着任何变更需要修改两处。
**建议**：明确分工——PRD 负责"做什么、为什么"（需求背景、AC、非目标），ADR 负责"怎么做、为什么这样做"（技术方案、依赖矩阵、实现步骤）。当前两者边界不够清晰，导致 ADR 承担了大量 PRD 内容。

### 3. 流水线缺乏"卡住自动升级"机制

编程师停滞 3 轮时，没有自动升级机制——Leader 似乎在被动等待超时后才介入。
**建议**：在 Worker 端增加心跳机制（如每 5 分钟向 Leader 发一条进度脉冲），Leader 端设置停滞检测（如连续 2 个周期无脉冲 → 自动 ping → 再 1 周期无响应 → 升级给用户）。

### 4. P0→P1→P2 三阶段在同一天跑完，缺少"停下来审视"的节奏

三阶段从规划（13:51）到 P2 完成（15:56）仅 2 小时，几乎没有阶段间的审视和调整。虽然三阶段都成功了，但这种"一口气跑完"的模式在更大项目中风险较高。
**建议**：对多阶段升级规划，每个阶段完成后强制做一次 mini-retro（甚至只是 Leader 在群里发一句"P0 完成，确认继续 P1？"），防止错误级联。

### 5. 变更记录模板未被使用

`docs/_TEMPLATE/变更记录.md` 模板存在，但本次没有产出对应的变更记录文档。QA 报告和发布报告承担了部分变更记录的功能，但缺少"逐文件变更行号+变更类型"的结构化记录。
**建议**：将变更记录作为实现的强制产出之一（编程师在提交代码后写），或在发布阶段由发布师从 git diff 自动生成。

## 六、P2 拆分影响评估

### 可维护性：⬆️ 显著提升

| 维度 | 拆分前 | 拆分后 |
|------|--------|--------|
| 单文件行数 | 5497 行 | HTML 754 行 + 6 模块均 <1600 行 |
| 报错定位 | `standalone.html:3847` 无模块信息 | `render.js:247` 模块+行号双定位 |
| 改动隔离 | 改宫位可能误伤排盘算法 | 6 模块物理隔离，互不侵入 |
| 代码导航 | 在 5497 行中搜索函数定义 | 按职责进入对应模块文件 |
| 多人协作 | 改同一文件，Git 冲突不可避免 | 不同模块可并行修改 |

### 测试覆盖：➡️ 持平（已足够好）

- 199 条回归断言全部保留在 main.js 中，无删减
- `?test=1` 机制不受模块拆分影响
- 新增了 `node -c` 语法检查（6 模块全通过）
- 新增了跨模块引用验证（5 个命名空间对象完整性检查）

测试覆盖没有因拆分而退化，反而增加了模块级别的语法检查。199 条断言 1ms 执行完毕，速度极快。

### 后续扩展性：⬆️ 大幅提升

| 扩展场景 | 拆分前 | 拆分后 |
|----------|--------|--------|
| 新增排盘算法（如紫微斗数） | 在 5497 行中找位置插入 | 新增 `ziwei.js` 模块，main.js 加一行引用 |
| 替换渲染引擎（如 Canvas 替代 Table） | 重写 render 函数时可能误伤算法 | 只改 render.js，algorithm.js 完全不动 |
| 引入第三方 UI 库 | 全局变量冲突风险高 | IIFE 命名空间隔离，冲突面小 |
| 单元测试 | 无法单独测试 algorithm | `node -e "require('./algorithm.js')"` 即可独立跑 |
| 迁移到 ES module | 全量重写 | ADR 已预留迁移路径——IIFE→export 是机械替换 |

### 技术债务清理

- ✅ `window._paipanData` 等全局变量从裸奔改为通过 `APP.getPaipanData()` 访问
- ✅ HTML onclick 从裸函数名改为命名空间前缀（`APP.doPaipan()`），不再依赖全局作用域
- ✅ 模块边界明确了哪些是"公开 API"、哪些是"内部实现"，为后续重构提供了契约基础
- ⚠️ gongwei.js 对 render.js 的"松散依赖"（通过 DOM 选择器而非函数调用）是隐含耦合，未来 render.js DOM 结构变更时需同步检查 gongwei.js

- 199 条回归断言全绿，零 FAIL
- UI 功能验证全部正常（11 项手动验证）
- 跨模块引用全部就绪

## 七、总结

P2 架构升级是一次**教科书级别的等价重构**：在 100% 保持功能不变的前提下，将一个 5497 行的单体 HTML 文件拆分为 6 个职责清晰的模块。核心亮点：

1. **ADR 质量极高**：逐函数行号清单+依赖矩阵+IIFE 模板+分阶段实施路线图，让编程师几乎可以"按图纸施工"
2. **回归测试零损伤**：199 条断言全绿，证明了拆分方案的精确性
3. **务实的技术选型**：IIFE+window 而非 ES module，基于 file:// 协议的硬约束做出正确取舍，同时预留了未来迁移路径

主要改进空间集中在**流水线工程层面**（时间戳采集、停滞检测、阶段审视），而非技术层面。如果这些流程改进落地，后续 P3+ 升级将更加顺畅。
