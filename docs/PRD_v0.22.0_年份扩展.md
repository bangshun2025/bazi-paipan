## 三、需求背景

**当前状态（v0.21.1）**：年份范围 1600-2100，12024 条节气数据、481 条农历信息。

**新需求**：邦顺测试王阳明 1472-10-31 22:01 男，被 `min="1600"` 阻止。需求扩展到 1000-2100，覆盖更早的历史人物。

**与 v0.21.0 的关键差异**：

| 维度 | v0.21.0「1900前支持」 | v0.22.0「1000-2100 扩展」 |

## 四、方案概述

### 4.1 总体思路

**数据层**：sxtwl 全量重新生成 LUNAR_INFO、LUNAR_NEW_YEAR、SOLAR_TERMS 三张表，覆盖 1000-2100（1101 年）。索引基准从 1600 平移为 1000。

**算法层**：在 `computeDaYun` 增加分级逻辑——出生年 ≥1400 起大运，<1400 返回空大运（四柱仍正常计算；流年仅依赖年柱干支，不受影响）。

**UI 层**：适配空大运状态，大运栏/起运信息区显示「—」或留空。

### 4.2 为什么 1400 是分界线

- **sxtwl 节气精度**：sxtwl 在 1400 年前后节气数据精度有显著差异。1400 年起可用 JPL DE440s 星历，前后秒级精度；1000-1399 年使用低精度外推，节气时刻误差可能达数分钟至数十分钟。
- **大运起运依赖节气**：起运计算 `qiYunDays()` 精确依赖节气时刻（出生到节气的天数差），时刻误差会放大到起运岁数的误差。对 1000-1399 年，这个误差不可接受，因此不显示大运。
- **四柱不受影响**：年柱仅依赖立春日期（日级精度足够），月柱仅依赖节气日期（日级精度足够），日柱依赖公历日期计数（完全精确）。1000-2100 全段四柱均可信赖。
- **流年不受影响**：`liuNianJZ(y)` 纯数学公式 `(y-4)%60`，无数据依赖。

## 五、需求详述

### 5.1 数据生成（sxtwl 全量重生）

**策略变化说明**：v0.21.0 采用「前置插入 300 年，旧数据不动」的策略以保证 1900-2100 逐日一致。v0.22.0 改为「全量重生」——所有数据统一由 sxtwl 生成。原因：
1. v0.21.0 的 1900-2100 旧数据来源不明确（可能是早期手工录入或另一数据源），与 sxtwl 生成数据可能存在微小差异（如个别节气时刻差几秒）
2. 扩展到 1000 年后数据量膨胀 2.3 倍（12024→26424 条 SOLAR_TERMS），维持「两段式」数据（新增+旧）的维护成本急剧上升
3. 统一数据源后，所有年份可交叉验证，数据质量审计变为可能
4. 现有回归测试 `?test=1` 的 199 条断言覆盖了关键排盘结果，全量重生后若断言失败即说明数据源差异——这反而是好事（发现历史数据问题）

**生成要求**：

```python
# 覆盖范围：1000-2100（1101 年）
# LUNAR_INFO: 1101 项，hex packed 32-bit 整数
# LUNAR_NEW_YEAR: 1101 项，[month, day]
# SOLAR_TERMS: 26424 项（1101 × 24），daysFrom20000101*86400+seconds
```

**编码格式**（与现有完全一致）：
- LUNAR_INFO: bits 0-3=闰月, bits 4-20=每月大小月, bit 20=闰月天数
- SOLAR_TERMS: `daysFrom20000101 * 86400 + seconds`，支持负 days
- LUNAR_NEW_YEAR: `[month, day]` 正月初一公历日期

**数据校验要求**：
1. 用 Leader 提供的 4 个历史人物锚点（苏轼/朱熹/文天祥/王阳明）反向验证生成脚本
2. 抽查边界年：1000、1001、1399、1400、1401 的农历/节气连续性和合理性
3. 与现有 v0.21.0 数据交叉比对 1600-2100 段：若有差异，记录差异清单供复盘决策（是接受新数据还是保留旧数据）

### 5.3 algorithm.js 改动

#### 5.3.1 lunarToSolar（L63）

| | v0.21.0 | v0.22.0 |
|--|---------|---------|
| 索引基准 | `idx = ly - 1600` | `idx = ly - 1000` |
| 数据长度 | `LUNAR_INFO.length` (481) | `LUNAR_INFO.length` (1101) |

> 不改逻辑，仅改常量 1600→1000。边界检查 `idx < 0` 对 <1000 年仍生效。

#### 5.3.2 getSolarTerm（L183）

| | v0.21.0 | v0.22.0 |
|--|---------|---------|
| 索引 | `(y - 1600) * 24 + n` | `(y - 1000) * 24 + n` |

> 不改逻辑，仅改常量。对 1000 年：idx=0×24=0；对 2100 年：idx=1100×24=26400。共 26424 项，idx 范围 0~26423，不越界。

#### 5.3.3 computeDaYun — 新增分级逻辑

**现状**（L483-L511）：无条件计算大运，`qiYunDays()` 依赖 `getSolarTerm()`。

**改后**：在函数开头增加年限判断：

```js
function computeDaYun(gender, nianGan, yueGan, yueZhi, birth) {
  // v0.22.0: 1000-1399 年不排大运（节气时刻精度不足以保证起运准确性）
  if (birth.getFullYear() < 1400) {
    return { daYun: [], qiYun: null, shun: null };
  }

  // === 以下为原逻辑，不改动 ===
  const yang = '甲丙戊庚壬'.includes(nianGan);
  // ...
}
```

**改动说明**：
- `daYun: []` — 空数组，UI 层据此显示空状态
- `qiYun: null` — 无起运信息，UI 层据此隐藏起运时间/交运文本
- `shun: null` — BuildShunLabel 返回空字符串
- 对 ≥1400 年，行为与 v0.21.0 完全一致

#### 5.3.4 yearPillar — 无需改动

`yearPillar(y)` 仅依赖 `(y-4)%60` 纯数学公式。1000 年前也可正确计算。

#### 5.3.5 dayPillar — 无需改动

`dayPillar(y, m, d)` 依赖 `Date.UTC(y, m-1, d)` 和与 1900-01-01 的天数差。JavaScript `Date.UTC` 安全范围 -271821 ~ 275760 年，1000 年远在安全范围内。

#### 5.3.6 liuNianJZ — 无需改动

纯 `(y-4)%60` 公式，流年始终可算。

### 5.4 render.js 改动（空大运适配）

render.js 中以下位置需适配 `daYun.length === 0` 或 `qiYun === null`：

| 位置 | 现状 | 问题 | 改后 |
|------|------|------|------|
| L336 | `curDy = daYun[curDyIdx]` | daYun 为空时 `daYun[0]` 为 `undefined` | 加守卫：`if (daYun.length === 0) { curDy = null }` |
| L337 | `pillar(curDy.gan, curDy.zhi)` | curDy 为空时报错 | 加守卫 |
| L353-354 | `qiYun.years, qiYun.months...` | qiYun 为 null 时崩溃 | 加守卫 |
| L357-358 | `qyStartDate.setFullYear(...)` | qiYun 为 null 时跳过 |
| 大运行渲染 | `for (let i = 0; i < daYun.length...` | daYun 为空时不进入循环 | **无需改动**——空数组循环自动跳过 |
| 起运文本渲染 | `出生后 ${joy} 年...` | joy 为 undefined | 条件渲染：`if (qiYun) { ... } else { 显示「—」 }` |

**预期 UI 行为（1000-1399 年）**：
- 四柱行：正常显示
- 大运行：留空（不显示任何大运柱）
- 起运/交运区：显示「—」或「（该年份暂不支持大运推演）」
- 流年区：正常显示（流年不依赖大运）
- 顺逆排标签：不显示（shun 为 null → BuildShunLabel 返回空）

## 九、风险评估

### 9.1 全量重生 vs 增量追加

**风险**：v0.21.0 的「1900-2100 逐日一致」承诺在 v0.22.0 中变为「与 sxtwl 输出一致」。如果 v0.21.0 的旧数据不是 sxtwl 生成的，可能有差异。

**影响范围**：差异如果存在，最可能出现在：
- 节气时刻差几秒（不影响月柱，因为月柱仅按日级判断）
- 个别农历年的大小月排列（极罕见）

**缓解措施**：
1. 实施时第一步：用 sxtwl 重新生成 1600-2100 段，与现有 constants.js 逐项比对
2. 若有差异：列差异清单，走邦顺确认（接受新数据 vs 保留旧数据）
3. ?test=1 的 199 条断言覆盖了关键排盘输出，作为自动化回归屏障

### 9.2 空大运状态传导链

**风险**：`computeDaYun` 返回空结构后，render.js 多处使用 `daYun`/`qiYun` 的属性可能崩溃。

**缓解**：
- PRD 已识别 4 个渲染守卫点（见 §5.4）
- 实施阶段建议先跑一次 1000 年排盘的渲染，逐项检查 UI 行

### 9.3 SOLAR_TERMS 索引偏移验证

**风险**：26424 项大数组，`(y-1000)*24+n` 的偏移计算如果写错一位，排查极难。

**验证方法**：
- 手工抽查：1000-01-01 取第一条节气（`SOLAR_TERMS[0]`），2100-12-31 取最后一条（`SOLAR_TERMS[26423]`）
- 脚本验证：遍历 1000-2100 每年，确认 `getSolarTerm(y, 0)` ~ `getSolarTerm(y, 23)` 的日期在该年公历范围内
  
### 9.4 yearPillar 对 <1000 年的行为

`yearPillar(y)` 在 y<4 时 `(y-4)%60` 产生负余数，但代码中 `if (idx < 0) idx += 60` 已妥善处理。对 1000 年，idx = (1000-4)%60 = 996%60 = 36，正确。无风险。
