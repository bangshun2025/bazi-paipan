# ADR · v0.31.0 节气边界 8 小时修正

- 版本：v0.31.0（2026-09-12）
- 状态：已实施（代码 + 断言 + 门禁 + 三端同步）
- 影响面：`algorithm.js`、`index.html` / `standalone.html`（内联）、`archive.js`、`main.js`、`scripts/`

---

## 1. 问题

同一份出生时刻，落在节气时刻之后 8 小时内的样本，月柱会落到**上一个节月**（连带人元司令与立春年柱），并推算出明显失真的起运。典型边界：

| 边界 | 真值（独立源） | 缺陷表现（v0.30.0） | 修正后 |
|---|---|---|---|
| 1987 立夏 | 5-06 09:05:35（HKO 09:05 / DE421 09:05:34） | 09:06 出生给「辰月」 | 「巳月」 |
| 2026 立春 | 2-04 04:01:51（HKO 04:02 / DE421 04:02:07） | 04:02–11:59 出生给「丑月」 | 「寅月」 |

关键点：**显示层的节气时刻一直是正确的**（列表/节气区显示 09:05:35），错的只有「换月判定」。所以缺陷对肉眼隐形，只有断言或跨源比对才能发现。

## 2. 根因

`getSolarTerm()` 查表返回「BJT-as-UTC」时刻 —— 其 `getUTC*()` 字段即北京钟表时间（实现：`new Date(ms2000 + days*86400000 + secs*1000 - 288e5)`）。调用侧一律用 `birthMs = Date.UTC(y, m-1, d, h, mi)`（同为 BJT-as-UTC），两端本应**直接比较**。

v0.23.4 在修复「节气当天零点截断」时，把比较式写成 `birthMs < term.getTime() + BJT_OFFSET`，即给节气边界**多加 8 小时**。该错误自洽地出现在三处：代码 6 个比较点、注释、以及 v0.23.4 的 CHANGELOG 描述（其引用的「立夏 17:05」恰为真值 09:05:35 + 8h）。

缺陷窗口：每个节气时刻起 8 小时。窗口内出生 → 月柱退一节月；同时 `renYuanSiLing` 会显示上一节气名与「后 N 日」，年柱立春边界同构。

未被既有断言拦住的原因：v0.23.4 的 T01/T02 取 06:30 与 18:00，两点同时位于「真值边界 09:05」与「错误边界 17:05」的同侧，**两种解释下结果相同**。

## 3. 决策：取消 +8h，单一基准

统一采用「BJT-as-UTC 单基准、两端直接比较」，删除全部 6 处 `+ BJT_OFFSET`（`BJT_OFFSET` 常量随之全库下线）：

- `monthPillar`：`lcMs` / `stMs` / `nextMs`
- `renYuanSiLing`：`stMs` / `nextMs`
- `paipan`：年柱立春 `lc2Ms`

`qiYunDays()`（起运天数）原本就未加 8h，与 `Date.UTC` 直接比较 —— 修正后全库基准一致，`getSolarTerm` 的返回约定写进 `monthPillar` 注释（「返回即 BJT-as-UTC，切勿再加 8 小时」）。

### 被否决方案

| 编号 | 方案 | 否决理由 |
|---|---|---|
| D1 | 给 `birthMs` 也 `+ 8h`（两端同错） | 等价成立，但把错误基准固化进两处，任何 `Date.UTC` 调用点都要记得加；且 `qiYunDays` 未加，会留下第三种基准 |
| D2 | 改 `getSolarTerm` 返回真 UTC | 改动面扩散到起运、节气列表、真太阳时等所有消费方，回归风险远大于收益 |
| D3 | 引入完整天文库重算节气表 | 属「节气表精度与年份范围」议题（见 §5），与本缺陷无关，不混做 |
| D4 | 只加断言、不改代码 | 断言会把错误行为固化为「期望值」 |

## 4. 门禁（防止复发）

| 门禁 | 内容 |
|---|---|
| `?test=1` T05–T11（10 条） | 以 HKO / DE421 真值为基准的边界断言：节气前 1 分钟 → 节气分钟双向换月、乙巳–丙午立春边界、1987 立夏 09:05 / 09:06、节气名与换月同源、起运回归 |
| `scripts/check-term-truth.js` | 无浏览器；vm 加载 `constants.js` + `algorithm.js`。12 节气 × {1987, 2026} × 3 采样点边界扫描 + 4 条显示层真值 + 10 条锚点。**以 v0.30.0 代码运行：24/24 边界项报警**（显示层全绿，证明该门禁方向正确） |
| `scripts/sync-module-inline.py` | 以「下一个模块标记」为切段边界（不能按 `<script>` 切，五个大模块共用同一块），比对 constants / algorithm / archive / render / main「外部 ≡ index 内联 ≡ standalone 内联」 |
| `scripts/check-release.sh` | 4 步 → 6 步（并入上述两项；任一失败退出码非 0） |

判据：`switchMs = 覆盖节气时刻的那一分钟`（04:01:51 → 04:02 换月；09:05:35 → 09:06 换月），断言与跨源比对均按此语义。

## 5. 三端一致性：为什么这次必须一起修

线上有三个产物入口：

- `index.html`（单体，内联全部模块）
- `standalone.html`（单体，内联全部模块）
- `standalone-split.html`（模块化入口，`<script src="*.js">` 加载**外部** `algorithm.js` 等）—— `/standalone` API 端点指向它

修复前 `algorithm.js` / `archive.js` 的外部文件落后于内联副本（缺 v0.23.1 农历取值修复、P0-01 `doPaipan` 守卫），且带有本次的 8h 缺陷。即：**修内联只修好了两个单体页，模块化入口仍是错的**。本次以「内联为真相源」重写两个外部文件（保留其原有头部注释块，头部版本号更新为内容实际变更的版本）。

约定：外部 `*.js` 文件头部版本 = 该文件**内容最后一次变更**的版本；内联副本头部为历史冻结标记，不随版本刷新。

## 6. 未覆盖 / 后续议题（不在本版范围）

- **节气表精度与年份范围**：表覆盖 1000–2100；`<1400` 年不排大运（既有约定）。远期若需更高精度，方向是以 JPL DE421 / HKO 数据重算表并扩充范围，属独立议题。
- **真太阳时**：`algorithm.js` 内建均时差为 Spencer 公式（分钟级精度，与秒级节气表不在同一量级），如需秒级需换用高精度均时差模型。
- **v0.30 T12 几何断言（既有，非本版引入）**：星曜设置页「60 行态免纵向滚动 ≤2px」依赖视口高度 —— 1512×771 下稳定溢出 11px（`scrollHeight 582 / clientHeight 571`，即浮层内容比可视区高一行的一角），更高视口下通过；**以 v0.30.0 原始字节运行同样复现**。CI 默认 800×600 视口 `wide()` 为假、不执行该分支，不影响部署门禁。观感影响：特定窗口高度下设置页出现约 11px 的细滚动条（与 v0.30「≥1280px 免滚动」的承诺不符），建议列入 v0.31.1 候选单独排期
