1. **为什么开发在错误文件上？** → Leader 发给产品经理的代码位置是开发文件目录，整个流程沿用了这个路径。

## 三、Bug 全景分析

### 3.1 Bug 清单

| # | 等级 | 发现方 | 现象 | 根因 | 修复成本 |
|---|------|--------|------|------|----------|
| 1 | P0 | QA | 标签行完全不渲染 | `<tr>` 在 `<div>` 中经 innerHTML 被浏览器剥离 | 1 行 |
| 2 | P0 | QA | 双胞胎面板缺失 | 单引号字符串含模板字面量语法 | 2 处各 1 行 |
| 3 | P0 | **用户** | 大运流年数据错乱 | 标签行插入后硬编码行索引偏移 | 7 行 |

### 3.2 Bug 模式识别

三个 Bug 属于三种不同类型，从简单到复杂：

```
Bug #1: API 误用（不懂浏览器 DOM 解析机制）
       ↓
Bug #2: 语法错误（字符串拼接 vs 模板字面量）
       ↓
Bug #3: 隐式假设破坏（新 DOM 结构改变了旧代码的索引前提）
       ↑
    最难发现——两个独立正确的操作组合后产生错误
```

这是**单文件单体架构的经典脆弱性**：当函数 A 向 DOM 中添加新元素，函数 B 通过硬编码索引访问 DOM——两者之间没有任何显式契约来保证"行的数量和顺序不变"。

### 3.3 为什么 Bug #3 最危险

| 维度 | Bug #1/#2 | Bug #3 |
|------|-----------|--------|
| 发现难度 | 低 — 新功能直接不工作 | 高 — 新功能正常，旧功能悄悄坏了 |
| 发现方 | QA（AC 驱动测试可拦截） | 用户（AC 驱动测试有盲区） |
| 测试覆盖盲区 | 无 — QA 首轮即发现 | 有 — 跨功能交互测试缺失 |
| 修复思路 | 直接改写法 | 要定位"两个函数之间的隐式耦合" |
| 复发风险 | 低 — 学会后不会再犯 | 高 — 只要还有硬编码索引，任何 DOM 改动都可能触发 |

## 六、对编排系统本身的改进建议

在本次编排中，有些问题不是 Worker 或 Leader 的能力问题，而是编排系统本身的工具/机制缺失：

### 6.1 编排启动时的上下文注入

**问题**：Leader 在启动时不知道用户的"真实部署文件路径"，依赖主动询问用户。

**建议**：编排启动时，系统注入一个 `deploy_target` 或类似环境变量，让 Leader 从一开始就知道最终交付目标。这等价于 CI/CD 中的"部署目标环境"——不在启动时明确就会在生产阶段爆雷。

### 6.2 并行任务识别

**问题**：架构师设计架构和发布经理建立 Git 基线可以并行，但 Leader 手动串行化了。

**建议**：编排系统可以为任务依赖图提供可视化或自动并行度分析，提醒 Leader"这两个任务没有依赖，可以同时派活"。

### 6.3 文件路径变更检测

**问题**：整个团队在同一文件上工作了三个版本，直到用户验收才发现"改错了文件"。

**建议**：编排系统可以在 Worker 读写文件时做路径审计——如果某个 Worker 改动的文件不在"部署目标"的路径下，系统发出警告。

## 七、关键经验教训

### ✅ 值得坚持

1. **PRD 写 AC 逐条编号**：架构成、开发、QA、发布全链路使用同一套 AC 编号对齐——这是信息传递零损耗的核心原因
2. **架构精确到行号**：15 个改动点全部带行号，开发可以按图施工
3. **QA Bug 报告含根因 + 修复建议**：让修复变成秒级操作
4. **全量重建而非增量更新**：架构选择的"方案 A：全量重建"在三个版本中被证明是最安全的选择
5. **Bug 修复走完整闭环**：定位→修复→回归→发布→复盘，不跳步骤
6. **复盘产出是资产而非形式**：v0.10.1 + v0.10.2 的两次复盘产出了 9 条可执行行动项

### ⚠️ 必须改进

1. **部署目标路径必须在启动时确认**：不依赖记忆、不猜测。这是本次编排最痛的教训。
2. **交付前必须有 smoke test**：开发→QA 之前加一道浏览器端到端验证门禁
3. **回归测试必须包含交互测试**：新功能 × 旧功能的交叉点，至少 3 条跨功能交互验证
4. **架构风险表必须增加"DOM 结构耦合"检查**：任何 DOM 结构变更都要审计硬编码索引的下游影响
5. **Leader 不能凭记忆给代码路径**：必须从用户或系统配置中获取，并在 PRD/架构阶段交叉验证
