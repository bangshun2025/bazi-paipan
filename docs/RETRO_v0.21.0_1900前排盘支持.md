```
1899 年最后一条 SOLAR_TERMS (gen_data):  -3,156,534,273
1900 年第一条 SOLAR_TERMS (existing):     -3,155,263,008
```

这个分析的价值不仅在于结论（"连续"），更在于建立了**数据扩展类版本的标准验证模式**：新数据与旧数据的交界处必须逐项比对，不能只相信"同源同格式"。

## 四、流程问题

### 问题 1：PRD 仍有被 ADR/Leader 修正的错误（严重性：低-中）

v0.21.0 PRD 有 2 处事实性错误 + 1 处不确定性：

| 错误 | 类型 | 影响 | 修正者 |
|------|------|------|:--:|
| LUNAR_INFO 181→201 | 数量错误 | 若按 181 计算，扩展后总计少 20 项，数组长度对不上 | ADR |
| 遗漏 archive.js + render.js 改动 | 范围遗漏 | 编辑已保存档案时拒绝 1600-1899；错误提示文案未更新 | Leader→ADR 记录 |
| 毛泽东时柱「庚子」待验证 | 不确定性 | 测试时发现实际输出「癸卯」，PRD 标注待验证故不判 Bug | 测试发现 |

**分析**：

- **数量错误**：本质是 PRD 撰写时的读码不仔细——`grep -c` 就能确认的数字被写错了。ADR 通过实测纠正，说明"ADR 独立验证 PRD"的机制在起作用。
- **范围遗漏**：archive.js 和 render.js 在 PRD 的"影响范围"表中确实没被列出。这属于需求分析阶段的信息缺失——产品经理可能不熟悉这两个文件的内部逻辑。Leader 作为最熟悉代码库的人补充发现，ADR 正式记录。
- **时柱不确定性**：PRD 标注"待验证"是诚实的做法，但暴露了一个流程缺口——**PRD 中未验证的数据断言，应该由谁来在什么阶段验证？** 测试阶段只能"发现差异"，不能"裁决谁对"——时柱的正确性需要邦顺或外部权威数据源确认。

**与 v0.20.1 的比较**：v0.20.1 PRD 也有签名错误（`persistSelected` 有参 vs 无参），同样被 ADR 纠正。连续两个版本的 PRD 都有被下游修正的错误——这不是个别版本的问题，是 PRD 撰写流程中的结构性现象。

**反思**：是否需要给 PRD 增加一个"提交前的自检清单"？例如：
- 所有涉及的文件名和行号是否实测确认？
- 所有硬编码数字（条目数、行数）是否 `grep -c` / `wc -l` 确认？
- 所有 API 调用签名是否与源码一致？

### 问题 3：缺少 RELEASE 文档（严重性：低）

v0.21.0 没有独立的 RELEASE 文档。v0.20.0 有 `RELEASE_v0.20.0.md`（内测版部署检查清单），但 v0.21.0 的发布信息只在 CHANGELOG 中体现。

**分析**：v0.20.2 和 v0.20.3（紧急修复版本）也没有 RELEASE 文档，这可能是发布角色的职责逐渐弱化的体现。CHANGELOG 确实覆盖了 RELEASE 的大部分内容（版本号、改动、测试结果），但缺少部署检查清单（如：本地三版 HTML 是否 md5 一致、线上 `?test=1` 是否全绿、GitHub Pages 是否更新）。

**建议**：要么正式取消 RELEASE 文档（统一用 CHANGELOG），要么定义 RELEASE 文档的最小模板（一页纸，5 项 checklist）。不要处于"有人写有人不写"的随机态。

### 问题 4：v0.20.1 复盘建议的落地率低——"Worker 协议修改"类建议的执行难题（严重性：低-中）

v0.20.1 复盘提出的 5 条建议中，只有自然发生的（L3 PRD 计数改进）和半自然发生的（L4 PRD 模板 section 持续使用）算落地。两条最高优先级建议（L1 Worker 超时通知、L5 测试代码 API 边界规则）完全未动。

**根因推测**：
1. **"建议"措辞缺乏执行主体**：复盘报告写"建议在 Worker 协议中增加……"，但没有指定谁来执行、通过什么流程执行
2. **协议修改需要编排层支持**：Worker 协议在 `.clackyrules` 和编排配置中，不是任何一个 Worker 能独立修改的
3. **复盘→执行之间缺少闭环机制**：v0.21.0 PRD 的「上版本复盘遗留项」section 引用的是 v0.20.0 的复盘（而非 v0.20.1），因为 v0.21.0 PRD 在 v0.20.1 复盘出来之前就写了——时序上存在 gap

**建议**：复盘报告中"建议修改协议/流程/模板"的条目，应配有明确的行动项格式：
- 执行者：谁来做？
- 触发条件：下一个版本的哪个环节执行？
- 优先级和 deadline：不能无限期搁置

而不是只有"建议……"这种开放式措辞。

## 五、关键决策点复盘

### 决策 1：扩展方式——纯数据扩展 vs 动态计算

| 选项 | 方案 | 改动面 | 风险 |
|------|------|--------|------|
| ✅ 采纳 | 纯数据扩展（用 sxtwl 生成 300 年数据，补到三张表头部） | ~7800 行数据 + 4 行常量 | 低——算法逻辑不碰 |
| ❌ 放弃 | 引入运行时历法库动态计算 | 需要引入新依赖、改算法、处理跨库兼容性 | 高——全量重测 |

**评价**：正确。在"1900-2100 不能有一字改变"的约束下，纯数据扩展是唯一安全的选择。代价是 constants.js 从 115K 膨胀到 211K（+83%），但对现代浏览器可忽略。

**值得注意**：这不是一个"架构决策"——PRD 阶段就已经锁定了方案。ADR 不过是验证和细化这个决策。这种"产品决策前置 → 架构验证"的模式在约束清晰的场景下效率很高，不需要架构师从零设计。

### 决策 2：gen_data 验证——Leader 介入非标准步骤

| 步骤 | 执行者 | 内容 |
|------|:--:|------|
| sxtwl 数据生成 | Leader | Python 脚本调用 sxtwl，输出 300 年三表数据 |
| 格式验证 | 架构师 | 比对 hex 格式、`[m,d]` 格式、packed 格式与现有数据一致 |
| 交叉验证 | 架构师 | sxtwl 反查全量匹配，1900 年逐项比对（±2s 内一致） |
| 边界验证 | 架构师 | 1899→1900 交界连续性量化分析 |

**评价**：这是非标准流水线环节。数据生成是一个非常规操作（开发和测试都不管），需要 Leader 有足够的技术判断力介入。建议在数据扩展类版本的 PRD 模板中增加"数据生成"section，明确由谁执行、用什么工具、验证标准是什么——不委托给编程师（编程师负责代码改动，不负责天文历法数据生成）。

### 决策 3：v0.20.1→v0.20.2→v0.20.3→v0.21.0 的版本线

时间线上看：

```
v0.20.0 常用宫位分级（功能）
  → v0.20.1 自动化断言补充（流程改进）
    → v0.20.2 紧急修复 index.html 排盘崩溃（线上事故）
      → v0.20.3 常用宫位双 tab 补同步（漏同步修复）
        → v0.21.0 1900 前排盘支持（功能）
```

**评价**：v0.20.2 和 v0.20.3 都是"同步遗漏"的修复——build_modules.py `\n` 缺陷导致的线上事故 + 宫位双 tab 漏同步。这两次修复的根因都可以追溯到 v0.20.1 复盘提出的 L2（build_modules.py 缺陷）以及 index.html/standalone.html 缺乏自动同步机制。

值得肯定的是，v0.21.0 的 ADR 显式加入了三版 HTML 一致性校验步骤（从 v0.20.2/0.20.3 的血泪教训中学到的）。但 build_modules.py 本身的问题仍未被修复——只是靠人工校验规避，而非从源头消除。

## 六、流程改进建议

### 建议 1：复盘建议需要"可执行"的落地格式，而非开放式建议（优先级：高）

**问题**：v0.20.1 复盘的 5 条建议中有 4 条未被正式落地，"建议在 XX 中增加 XX"的开放式措辞导致没有明确的执行主体和触发条件。

**具体建议**：复盘报告的每条建议附带以下三个字段：

```markdown
| 编号 | 行动 | 执行者 | 触发条件 |
|------|------|:------:|------|
| L1 | Worker 协议增加超时通知规则 | Leader（修改编排配置） | 下一个版本的复盘后执行，或直接纳入 DEVELOPMENT.md 更新 |
```

这样，下一版本的 PRD「上版本复盘遗留项」section 可以直接引用此表，标注"是否执行"。

### 建议 2：PRD 提交前增加自检清单（优先级：中）

**问题**：连续两个版本（v0.20.1 和 v0.21.0）的 PRD 都有被下游修正的事实性错误。

**具体建议**：在 PRD 模板末尾增加一个"PRD 自检清单"：

```markdown
## 自检清单（提交前确认）

- [ ] 所有文件路径是否实测确认（而非凭记忆写）？
- [ ] 所有硬编码数字（条目数、行数、版本号）是否 `wc -l` / `grep -c` 实测？
- [ ] 所有 API 调用签名是否与源码一致（包括参数有无）？
- [ ] 改动的文件范围是否覆盖了所有受影响文件（不只是主要文件）？
- [ ] 「上版本复盘遗留项」是否已逐条标注处理方式？
```

### 建议 3：数据扩展类版本应有"数据生成"步骤的明确规范（优先级：中）

```markdown
### 数据扩展类版本的数据生成规范

当版本涉及 constants.js 中的历法数据表扩展（LUNAR_INFO / LUNAR_NEW_YEAR / SOLAR_TERMS）时：
1. **数据源**：sxtwl（寿星万年历）Python 库离线生成，不进入运行时
```

## 十、总结

v0.21.0 是一次**目标清晰、ADR 质量突出、回归坚如磐石、但 PRD 和测试环节仍有可改进空间**的功能交付。

**数字说话**：
- 1600-2100，501 年覆盖——300 年新增，201 年不变
- constants.js 115K→211K，+83%——全是数据，零逻辑
- algorithm.js 只改 2 个数字（1900→1600）
- 211/211 全绿，1900-2100 逐日一致

**最大的流程价值**：

1. **ADR 独立价值终于兑现**：502 行的 ADR 不只是翻译 PRD，而是独立发现了 2 处 PRD 错误、做了 gen_data 交叉验证、量化分析了边界连续性、给出了 5 项风险的缓解措施。这是 v0.16.0 复盘以来持续追求的"ADR 不只是翻译"的质变点。

2. **v0.20.1 复盘预警的问题在 v0.20.2 应验了**：build_modules.py `\n` 缺陷导致线上事故——复盘预警的延迟落地有真实代价。这强化了一个结论：流程改进建议如果只是"建议"格式而没有明确的执行主体和触发条件，大概率不会被执行。

3. **数据扩展的标准化路径已跑通**：sxtwl 生成 → 格式验证 → 交叉验证 → 边界连续性分析 → 实现 → 三版 HTML 同步 → 回归验证。后续类似版本（扩展到 1400 年）有现成引路。

**一句话**：v0.21.0 做了一件困难但正确的纯数据扩展（算法一行不动），ADR 以历史最高质量的独立验证撑住了这个承诺，而 v0.20.1 复盘预警的落地延迟给了我们一个更重要的教训——**复盘建议必须附带执行主体，否则只是存档**。
