## 四、流程问题

### 问题 1：A2 失败暴露「测试代码绕过公开 API」的隐性陷阱（严重性：中）

**现象**：测试师首次验证时 `GWFav:A2 做功仍在selected` 失败。根因是测试代码直接赋值 `GONGWEI.selectedGongWei = ["信息","做功"]`——但 `initGongWeiData()` 中对 `selectedGongWei` 的重新赋值切断了导出引用，`persistSelected()` 操作的是内部闭包变量而非被覆盖的导出属性。

**本质**：这是"值导出 vs 闭包变量"的经典 JavaScript 陷阱。`let selectedGongWei = []`（闭包变量）被 `window.GONGWEI` 导出为直接引用——看似是一个变量，但 IIFE 内部重赋值后，外部引用指向旧值，内部引用指向新值。测试代码不具备访问内部闭包变量的能力，只能通过公开 API 操作。

**修复**：改用 `clearSelection()` + `toggleSelect()` 公开 API（gongwei.js 零改动）。

**流程教训**：
- 测试代码和功能代码一样，受同一个 API 边界的约束。如果测试需要绕过 API 直接操作内部状态，说明 API 设计不完整——但这里 API 是完整的，只是测试师（以及 PRD）没有意识到应该用 API 而非直接赋值
- **ADR 已经预判了这个陷阱**（R1："persistSelected() 无参但 PRD 传了参数——实现时若照抄 PRD 会导致 A2 断言假通过"），但只预判了"参数被忽略"这一半——实际陷阱比预判更深（整个引用被切断）
- 这种陷阱在"纯测试代码不改功能代码"的版本中尤为危险——因为注意力集中在测试逻辑上，容易忽略 API 边界的细节

**建议**：在 PRD/ADR 中，凡是涉及 `window.XXX.yyy = [...]` 直接赋值的测试代码，应增加一个校验步骤——确认该属性是"值引用"还是"getter/setter"还是"闭包导出引用"。或者更简单的规则：**测试代码永远用公开 API，不用直接赋值**。

### 问题 2：测试师中途两次卡住，靠 Leader 催促恢复（严重性：低-中）

**现象**：测试阶段，测试师两次进入无进展状态，Leader 主动催促后才恢复推进。这种"卡住但不求助"的行为模式在编排流水线中会放大延迟——Leader 不知道 Worker 是否遇到问题，Worker 也没有主动同步状态。

**根因推测**：结合本次测试的具体情况——

1. **第一次卡住**：很可能在 A2 失败后。测试师发现失败但不确定是自己操作问题还是代码 bug，陷入"自查循环"而未及时横向沟通（问编程师或架构师）。——这与 v0.20.0 复盘中"Worker 之间缺少心跳/进度可见性"的观察一致。

2. **第二次卡住**：standalone.html 打开后 "GONGWEI 加载失败"（实际上不是 GONGWEI 模块问题，而是 `build_modules.py` 遗留的 `\n` 字面换行破坏 JS 语法）——测试师一度误判为模块加载失败，后自行定位并修复。这次卡住有合理成分（排查需要时间），但同样没有在排查期间向 Leader 发送进度更新。

**建议**：在 DEVELOPMENT.md 或 Worker 工作协议中增加一条规则——"超过 10 分钟无明确进展，必须向 Leader 发一条状态消息（哪怕只是'正在排查 X，暂无结论'）"。这不是 micromanagement，而是防止 Leader 在不知情的情况下等待。

### 问题 3：`build_modules.py` 是拆分工具非内联工具——ADR「无需运行」表述有误（严重性：低）

**现象**：ADR §目标文件信息中写"`build_modules.py` 无需运行——`main.js` 的 `?test=1` 回归测试区不在内联路径中"。这个判断**在 main.js 层面**是正确的——main.js 确实不在 `build_modules.py` 的内联列表中。

但 `standalone.html` 的同步是**手动**的：内联版（standalone.html）的 gongwei.js 代码来自 `build_modules.py` 的输出（gongwei.js→standalone-split.html←build_modules.py→standalone.html），而 `build_modules.py` 在将 gongwei.js 内联到 standalone.html 时，存在 `\n` 转义符被转换为字面换行符的已知缺陷。这导致初次打开 standalone.html 时 GONGWEI 模块加载失败。

**根因**：ADR 把"不改 JS 模块逻辑"等价于"不需要运行构建工具"，忽略了 standalone.html 的同步是手动操作且依赖 build_modules.py 的输出质量。

**教训**：
- `build_modules.py` 的定位应在 SYSTEM.md 或 DEVELOPMENT.md 中明确：它是拆分工具（将 standalone.html 拆分为模块），而非内联工具（standalone.html 是手动/半自动同步的）
- 任何涉及"两个版本的 HTML（standalone-split.html ↔ standalone.html）"的改动，都应有一个验证步骤确认内联版可用——即使"逻辑上"不该影响
- 测试师自行修复了 `\n` 问题——这说明 Worker 具备自主排查能力，但也说明 `build_modules.py` 的这个缺陷已经存在但未被正式记录和修复

### 问题 4：测试断言计数口径混乱（严重性：低）

PRD 标题写"6 条 GWFav 断言"，实际实现是 12 条子断言。PRD 的"6 条"是按场景（A1-A6）计数，实现按 `tests.push(eq(...))` 调用次数计数。虽然测试报告正确标为 12 条，但 PRD→ADR→TEST 之间的计数跳跃（6→6→12→211）会在后续版本引用时造成困惑。

**建议**：PRD 中区分"场景数"和"断言数"，例如写"6 个场景（共 12 条子断言）"。

## 五、关键决策点复盘

### 决策 1：A2 修复——改测试代码还是改 gongwei.js？

| 选项 | 方案 | 改动面 | 风险 |
|------|------|--------|------|
| ✅ 采纳 | 测试代码改用 `clearSelection()` + `toggleSelect()` | 仅 main.js 的 ~3 行 | 无——公开 API 已有测试覆盖 |
| ❌ 放弃 | 在 gongwei.js 中将 `selectedGongWei` 从直接引用改为 getter/setter | gongwei.js 结构改动 + 全量回归重跑 | 影响所有依赖 `selectedGongWei` 的代码 |

**评价**：正确。这是"问题在调用方，不在被调用方"的典型案例。公开 API 已完整，测试代码不该绕过它。修复测试代码而非修改 gongwei.js 保持了最小改动面。

### 决策 2：L3（时间戳自动采集）评估为"不做"

**评价**：合理。Leader 每次派活/收汇报已有自然时间戳（消息记录），手动推算够用。建立自动化机制需要改编排层或引入新工具，成本远超收益。

### 决策 3：L4（Worker 进度可见性）纳入 P3 backlog 而非本版本

**评价**：合理。但这意味着在 P3 之前，Worker 卡住不求助的风险会持续存在。本次测试师两次卡住的经验表明：**即使不建完整的流水线日志系统，一条简单的"超过 10 分钟无进展→发状态消息"规则也能大幅改善可见性**——这条规则的落地成本为零（只需在 Worker 协议里加一句话），不应等到 P3。

## 六、流程改进建议

### 建议 1：Worker 工作协议增加"无进展超时通知"规则（优先级：高）

**现象**：测试师两次卡住不求助/不汇报，Leader 需主动催促。

**具体建议**：在 DEVELOPMENT.md 或 Worker 工作协议中增加：

> **超时通知规则**：任何 Worker 在执行任务时，若超过 10 分钟无明确进展（卡在排查、不确定下一步、等待外部依赖），必须向 Leader 发送一条简短状态消息——哪怕只是"正在排查 X 问题，暂无结论"。这不是 micromanagement，而是让 Leader 知情以做出调度决策。

这条规则的改造成本为零（不需要新工具），但能显著减少编排流水线中的"沉默等待"。

### 建议 2：`build_modules.py` 的 `\n` 转义符缺陷应正式记录并修复（优先级：中）

**现象**：`build_modules.py` 在将 gongwei.js 内联到 standalone.html 时，`\n` 转义符被转换为字面换行符——这是已知缺陷（测试师自行修了两次），但未在 SYSTEM.md 或 DEVELOPMENT.md 中正式记录。

**具体建议**：
1. 在 SYSTEM.md 的"已知缺陷"或"构建工具" section 中记录此问题（含复现条件和临时修复方法）
2. 评估是否在下一个小版本中修复 `build_modules.py` 本身（从源头消除而非每次手工修）
3. 在开发和发布 checklist 中增加「standalone.html 语法校验」（至少 `?test=1` 打开确认）

### 建议 3：PRD 中区分"场景数"和"断言数"（优先级：低）

**具体建议**：在 PRD 模板的 AC 表格或需求描述中，当场景数和断言数不一致时，显式标注两者。例如："6 个场景（A1-A6，共 12 条子断言）"。避免下游引用时产生计数困惑。

### 建议 4：沉淀「上版本复盘遗留项」section 的经验（优先级：低）

**经验**：PRD 模板新增一个强制填写的 section，是"零成本修复流程闭环断裂"的有效模式。已在本版本中验证有效。

**沉淀方式**：将本经验写入 DEVELOPMENT.md 的"迭代式开发流程"章节，作为"每个功能迭代的标准流程"的补充说明——"产品经理输出 PRD 时，必须查阅上一版本复盘报告，并在「上版本复盘遗留项」section 中逐条标注处理方式"。

```markdown
### 测试代码铁律

- 测试代码**必须**使用公开 API 操作状态，**禁止**直接赋值 `window.XXX.yyy = [...]`
- 原因：gongwei.js 等模块导出的是"闭包变量的直接引用"——IIFE 内部重赋值后，外部引用可能指向旧值。公开 API（如 `clearSelection()` + `toggleSelect()`）内部操作的是正确的闭包变量
- 如发现公开 API 不足以表达测试需要的操作 → 报告 Leader，讨论是否扩展 API，而非绕过
```

### 9.3 补充：`build_modules.py` 定位说明（建议加在 §三 相关项目的 SYSTEM.md）

```markdown
### build_modules.py 定位

- **性质**：拆分工具（将 standalone-split.html 中的内联模块拆分为独立 JS 文件），非内联工具
- **已知缺陷**：将 gongwei.js 内联回 standalone.html 时，`\n` 转义符被转换为字面换行符，破坏 JS 语法。临时修复：手动替换字面换行为 `\\n`。根因待修。
- **验证步骤**：任何涉及 standalone.html 的改动后，必须 `?test=1` 打开确认断言全绿
```

## 十、总结

v0.20.1 自动化断言补充是一次**目标明确、执行有波折但结果优秀**的小版本交付。

**数字说话**：
- 12 条新断言，199→211，全绿
- gongwei.js 零改动——纯测试基础设施升级
- 打破了连续 4 个版本的自动化断言零增长僵局

**最大的流程价值**：不是 12 条断言本身，而是——

1. **复盘闭环首次跑通**：v0.20.0 复盘的建议（L1、L2）在 v0.20.1 中全部落地，"PRD 模板加 section"的低成本模式被验证有效
2. **暴露了测试基础设施的两个隐性知识缺口**：
   - "值导出 vs 闭包变量"陷阱——测试代码绕过公开 API 的风险（A2 失败）
   - `build_modules.py` 的 `\n` 字面换行缺陷——工具链的已知但未记录的坑
3. **验证了 Worker 进度可见性问题的实际影响**：测试师两次卡住不求助，恰好印证了 v0.20.0 复盘 §六.3 的前瞻性判断——"缺少流水线日志"不仅是复盘不便，在 Bug 发生时尤其危险

**一句话**：v0.20.1 做了它该做的事（补断言），顺便把流水线的几块隐性短板照了出来——这是"小版本暴露大问题"的经典案例。
