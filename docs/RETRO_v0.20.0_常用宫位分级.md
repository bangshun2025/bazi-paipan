## 三、编排机制复盘（orch_dd3030211180 复用评估）

> Leader 特别要求关注：从 P2 架构升级沿用的 6 worker 编排复用顺畅度、消息派发/轮询机制的稳定性。

### 3.1 编排复用顺畅度

v0.16.0 P2 架构升级建立了 orch_dd3030211180 下的六角色编排（产品经理 / 架构师 / 编程师 / 测试师 / 发布师 / 流程师）。v0.20.0 在同一编排下运行第二次完整流水线。

**顺畅点**：
- **Worker 角色认知一致**：各 Worker 无需重新理解流水线协议，直接进入执行——PRD→ADR→实现→测试→发布→复盘的标准流程已被内化
- **文档产出格式统一**：PRD 333 行 / ADR 375 行 / TEST 192 行 / RELEASE 87 行——文档长度和深度与功能规模成比例，没有出现 v0.16.0 ADR 566 行那种"架构升级特供"的超长文档
- **交接摩擦低**：ADR 直接引用了 PRD 的验收标准编号（AC01-AC14 + AR01-AR08），测试报告逐条对照 AC/AR 编号验证。跨 Worker 的文档引用链干净

**可改进点**：
- **Worker 之间缺少"握手确认"**：从素材看，编程师在实现后、测试师在测试前，没有显式的"我完成了，请接手"消息。流水线依赖 Leader 的中转派发，增加了一次往返。如果 Worker 之间可以直接交接（编程师完成 → 直接通知测试师 + 抄送 Leader），可减少等待时间
- **缺少中间状态同步**：例如编程师在实现过程中是否遇到了 ADR 未覆盖的细节？测试师在手工测试中是否有不确定的行为需要编程师确认？这些横向沟通在素材中没有证据。可能发生了但没有记录，也可能确实没有——22/22 全绿暗示后者

### 3.2 消息派发/轮询机制稳定性

**观察到的稳定性证据**：
- 六角色产出齐全、格式规范、内容无缺失——说明 Leader→Worker 和 Worker→Leader 的消息链路在整条流水线中稳定运行
- 各 Worker 产出文档的路径和引用正确（无人找错文件或路径），说明 Leader 的任务描述精度足够
- 编排复用无"路径漂移"——项目从 `10-开发项目/八字排盘功能/` 迁移到 `10-开发项目/软件-八字排盘/` 后，所有 Worker 的产出路径正确更新（docs/ 目录统一），未出现旧路径残留

**观察到的潜在风险**：
- **复盘环节前的上下文压缩**：本次复盘启动时，我的会话历史已被压缩为 summary chunk。虽然通过 summary + chunk 文件 + Leader 重新派发任务恢复了上下文，但这种"最后环节的 Worker 被压缩后再启动"是编排复用的一个风险点——如果压缩摘要丢失了关键信息（如 Leader 在流水线中途做出的微调决策），复盘质量会受影响

### 3.3 编排改进建议

1. **流水线消息日志**：Leader 在每次 Worker 任务完成时，向一个公共 channel（如所有 Worker 可见的"流水线日志"）追加一条简短记录。流程师复盘时可直接查阅，无需从各 Worker 文档中反推

## 四、关键决策点

### 决策 1：新增独立 localStorage key（`bz_gongwei_fav`）vs 在现有 group 对象上加字段

| 维度 | 采纳方案（`bz_gongwei_fav` 独立键） | 备选（在 `gongWeiGroups[i]` 加 `isFav`） |
|------|--------------------------------------|------------------------------------------|
| 排序独立性 | ✅ 常用排序与全部排序完全解耦 | ❌ 两个排序维度无法共存于同一数组 |
| 数据迁移 | ✅ 检测 key 缺失 → 一次性自动初始化 | ❌ 需遍历数组逐个加字段 |
| 模式一致性 | ✅ 与 `bz_gongwei_selected`（`string[]`）一致 | ❌ 引入混合数据模式 |

**评价**：正确。PRD 核心需求——「全部宫位排序不影响常用宫位顺序」——天然要求两个独立有序结构。备选方案需要在两个排序维度间做跨数组同步，复杂度高且易出错。

### 决策 2：旧用户迁移——全部默认常用

**评价**：务实。「老用户升级后零感知变化」是数据迁移的黄金标准。ADR 明确写了迁移后清洗幽灵名称（`findGroupByName !== null` 过滤）——这是对 v0.16.0 复盘教训（跨文档不一致）的主动防御，说明架构师在复用编排中积累了经验。

### 决策 3：设置页 tab 用纯 JS DOM 切换

**评价**：与现有 `gzSettingsView`（二态→三态）机制一致，改动面最小。实际实现采用了混合方案（HTML 层面两个独立 div + JS 端 `switchGzTab()`），与 ADR"纯 JS 切换"的描述有轻微偏差，但不影响功能。

### 决策 4：☆ Unicode 字符 vs checkbox vs SVG

**评价**：☆ 是低摩擦选择。但需注意 PRD AV02 要求触控区 ≥24×24px——测试报告未专门验证移动端的 ☆ 辨识度。这是一个小缺口。

### 决策 5：「默认」按钮不引入额外状态标记

**评价**：正确。用户点击默认 = 显式意图，避免了"是否手动调整过"的额外状态管理。ADR R4 诚实标注了"误点后无法撤销"的 UX 限制。

## 五、遇到的问题

### 问题 1：v0.19.0 复盘建议未被追踪和落地（严重性：中）

**现象**：v0.19.0 复盘报告（流程师 worker_07d7b529，2026-08-09）提出了两条高优先级建议：
1. **补隐私回归断言**：v0.19.0 上线了隐私模式但 199 条内置回归零增长。建议在 v0.20.0 补充
2. **回归集基线化**：建议每个版本强制「新功能对应新断言」

两条建议在 v0.20.0 中均未落地：
- 内置回归仍为 199 条，零增长
- 22 条 AC+AR 全部为手工验证，无新增自动化断言

**影响**：连续第二个版本功能上线而回归集零增长。v0.19.0（隐私）→199 条；v0.20.0（常用宫位）→199 条。自动化覆盖面在功能增长中相对萎缩。

**根因**：复盘→改进行动的闭环断了。v0.19.0 复盘报告产出后，没有机制确保其建议被纳入 v0.20.0 的 PRD/ADR/测试要求中。

### 问题 2：PRD/ADR 行数预估偏差约 50%（严重性：低）

| 来源 | 预估 | 实际 | 偏差 |
|------|------|------|------|
| PRD §8 总计 | ~200 行 | 315 行 | +57% |
| ADR §八 总计 | ~215 行 | 315 行 | +46% |

**根因**：PRD 低估了"数据一致性同步"的工作量——`updateGroup()`、`deleteGroup()`、`restoreFromTrash()`、`resetToDefaults()` 四个函数都需要新增 `bz_gongwei_fav` 同步，PRD 只给了 ~15 行。模式与 v0.16.0 的 constants.js 翻倍（450→857）类似——"牵一发动全身"的数据模型变更，预估容易低估级联影响。

### 问题 3：测试缺少自动化断言覆盖（严重性：中）

22 条 AC+AR 全部通过手工验证 + `localStorage` 直读 + DOM 断言，零新增 `?test=1` 自动化断言。常用宫位的核心路径（fav 数据迁移、☆ 切换、级联清理、默认排序恢复）在后续版本可能被意外破坏而自动化回归无法发现。

**具体建议**（可在 v0.20.1 补 5-8 条断言）：
- `getFavGroups()` 返回顺序与 `bz_gongwei_fav` 一致
- 级联清理：从 fav 移除 → `selectedGongWei` 同步移除
- 旧用户迁移：清除 `bz_gongwei_fav` → 自动重建为全部 groups
- 默认排序：`resetFavOrder()` 后 fav 顺序与 groups 相对顺序一致
- 新增宫位组默认不在 fav 中

## 六、流程可改进之处

### 1. 复盘闭环断裂——建议需要追踪机制（优先级：高）

v0.19.0 复盘的两条核心建议在 v0.20.0 中完全未落地。

**建议**：在 PRD 模板中增加「上版本复盘遗留项」section，要求产品经理逐条确认。最低成本方案：Leader 在派发 PRD 任务时附带上一版本复盘报告的路径。

### 2. 阶段时间戳采集仍未解决（延续 v0.16.0 问题）

**建议**：最低成本方案——Leader 在派活时和收到完成汇报时各记录一条带时间戳的日志消息。

### 3. Worker 进度可见性不足（编排机制观察）

流程师无法从素材中还原编程师是否有过短暂停滞、测试师是否遇到不确定行为。

**建议**：Leader 维护一条"流水线日志"channel，每次 Worker 任务完成时追加简短记录，流程师复盘时直接查阅。

### 4. PRD/ADR 信息重叠问题有好转但仍存在

PRD（333 行）和 ADR（375 行）在数据模型、约束表等方面仍有 ~40% 重叠。但 ADR §2.3「关键观察」section 开始产生独立价值——从架构角度补充了 PRD 未覆盖的技术细节（如 `buildGongWeiTagRows()` 的纯函数特性）。

**建议**：延续 v0.16.0 复盘建议——PRD 专注"做什么、为什么"，ADR 专注"怎么做、为什么这样做"。当前可进一步精简重叠部分。

## 八、总结

v0.20.0 常用宫位分级是一次**实现质量优秀、编排运转顺畅、但反馈闭环有缺口**的功能交付。

**亮点**：
1. **零 Bug 交付**：22/22 全绿，实现→测试→发布三环无返工。ADR 的逐函数行号实测 + 数据一致性约束表功不可没
2. **编排复用成熟**：orch_dd3030211180 在第二个完整流水线中运转顺畅——Worker 角色认知一致、文档格式统一、引用链干净、路径无漂移。编排本身不是瓶颈
3. **ADR 开始产生独立价值**：§2.3「关键观察」section 和防御性设计（迁移后清洗幽灵名称）表明架构师不再只是"翻译 PRD"，而是主动发现 PRD 未覆盖的技术细节
4. **跨版本经验传承有迹可循**：v0.16.0 复盘的文档不一致教训 → v0.20.0 ADR 更严谨的源码验证

**主要问题**：
1. **复盘→改进行动的闭环断了**：v0.19.0 两条核心建议在 v0.20.0 中完全未落地。这是流程层面最需要修复的环节
2. **自动化测试覆盖持续萎缩**：连续四个功能版本零新增断言，199→199→199→199
3. **Worker 进度可见性不足**：缺少流水线日志，复盘依赖文档反推

**最关键的一项改进**（只做一件事）：在 PRD 模板中增加「上版本复盘遗留项」section，强制产品经理在新版本启动时逐条确认。零成本、高收益——不需要新工具、不需要改协议。
