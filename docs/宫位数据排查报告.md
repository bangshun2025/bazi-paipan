## ② 用户自定义宫位数据存在哪、如何找回

### 存储位置（关键）

用户自定义宫位**全部存浏览器 localStorage**，按浏览器 **origin（协议+域名+端口）隔离**：

| localStorage 键 | 内容 | 引入版本 |
|---|---|---|
| `bz_gongwei_groups` | 宫位分组数据（14 组预置 + 用户新增/修改的组与标签） | v0.13.0 |
| `bz_gongwei_trash` | 宫位回收站 | v0.13.0 |
| `bz_gongwei_selected` | 勾选中的宫位 | v0.10.0 |
| `bz_gongwei_fav` | 常用宫位列表（用户「常用宫位都调过」对应的数据） | v0.20.0 |

- 读写逻辑见 `gongwei.js`：`loadGroups()/loadTrash()/loadSelected()/loadFav()` 与 `persist*()`；
- **未接 Supabase**：v0.24.0 的云端化只覆盖「档案记录」（records.js），宫位自定义数据仍在 localStorage，**无云端副本**；
- 读取容错（`loadGroups()`）：localStorage 中 `bz_gongwei_groups` 缺失 / JSON 损坏 / 空数组 → 静默调用 `initGongWeiGroups()` 重建默认 14 组。**这是「数据变回默认」的直接机制。**

### 为什么用户感觉「数据不一样」——根因判定

公测版与内测版是**不同的 origin**，localStorage 天然不互通：

| 环境 | 入口 | origin |
|---|---|---|
| 公测版（线上 v0.23.4） | GitHub Pages：`https://bangshun2025.github.io/bazi-paipan/standalone.html`（README 曾写 clacky.github.io，以实际访问为准） | `https://bangshun2025.github.io` |
| 内测版（v0.24.0） | Clacky 扩展：`http://localhost:7070/api/ext/bazi-paipan/standalone` 或侧边栏面板 / file:// 直开 | `http://localhost:7070` 或 `file://` |

用户原来在公测版调好的宫位数据存在公测版 origin 的 localStorage；切到内测版（不同 origin）后读取不到 → 触发 `initGongWeiGroups()` 重建默认 → 显示默认宫位，观感「数据变了」。

### 找回方案

**方案 A（首选，数据仍在原公测版浏览器里时）——手动迁移 localStorage：**

1. 打开原公测版页面（用户以前用的那个地址，如 `bangshun2025.github.io/bazi-paipan/standalone.html`）；
2. 按 F12 打开 DevTools → **Application（应用）→ Local Storage → 选择公测版 origin**；
3. 依次复制 4 个键的值：`bz_gongwei_groups`、`bz_gongwei_trash`、`bz_gongwei_selected`、`bz_gongwei_fav`；
4. 打开内测版页面 → DevTools → Application → Local Storage → 选择内测版 origin；
5. 依次点击各键 → 粘贴原值 → 回车保存（键名一致，直接覆盖）；
6. 刷新内测版页面 → 宫位数据恢复。

> 注意：值很长（JSON），复制时确保完整；粘贴后确认 Local Storage 条目已更新。

**方案 B（原浏览器 localStorage 已被清理 / 换了浏览器）——无法找回：**
- 自定义宫位从未上云，无服务端备份；`bz_gongwei_*` 键被清空即永久丢失，只能接受默认宫位后重新调。

**方案 C（推荐后续做）——应用内导入/导出：**
- 在「宫位设置」面板增加「导出配置 JSON / 导入配置 JSON」按钮（gongwei.js 数据层已具备 JSON 序列化能力，加两个函数即可），用户可随时备份到本地文件，跨环境迁移不再依赖 DevTools 手抄。

## ③ 与用户自定义数据的冲突标注

- **v0.24.0 未改任何宫位默认数据**（GONGWEI_MAP 与 v0.23.4 完全一致），因此**不存在「新版默认数据覆盖用户自定义」的冲突**；
- 真正的冲突是**环境切换导致的默认值回落**：内测版显示的是内置默认 14 组（信息/认知/功能/做功/亲缘/兴趣/场景/人设/客户/系统/关系/圈层/生理/记忆），而用户以为应该是他在公测版调过的分组/标签/常用宫位；
- 若用户两个环境都用过并各自改过数据，再次切换时会看到两套不同状态——这也是「不一致」的另一种表现，本质仍是 localStorage 分 origin 存储。

## ④ 后续迭代保护建议

1. **短期（1 个迭代内）**：宫位设置面板增加「导出/导入 JSON」；导入时做 schema 校验 + 备份旧数据（导入前把当前 `bz_gongwei_groups` 备份为 `bz_gongwei_groups_backup_<时间戳>`）。
2. **中期（随账号体系落地）**：宫位配置上云——Supabase 新增用户配置表（如 `user_gongwei_config`：user_id + 4 个 JSON 字段），登录后以云端为准拉取，未登录回落 localStorage；避免重蹈档案「本地→云端」迁移时用户数据静默丢失的坑。
3. **防静默重置**：`loadGroups()` 在数据缺失/损坏时不要直接重建默认，改为「备份损坏数据 → 提示用户」或「重建默认但保留 backup 键」，杜绝无感知覆盖。
4. **版本迁移保护**：localStorage 数据加 schema 版本号，升级时做 merge（旧数据 + 新默认字段补齐），而非整体覆盖。
5. **文档**：在 README/部署报告中明确「自定义宫位仅存本机浏览器 localStorage、按环境隔离」，避免用户跨环境使用产生误解。
