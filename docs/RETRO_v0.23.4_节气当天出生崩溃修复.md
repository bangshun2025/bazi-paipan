## 三、流程问题与根因

### 问题 1：节气零点比较的坑为什么没被早期测试覆盖？⚠️（核心复盘问题）

**事实链**：monthPillar 的「节气日期零点截断」逻辑自 v0.9.3（2026-07-24 排盘修复）以来长期存在，期间经历 v0.16.0 架构拆分、v0.20.0-0.23.0 多版本断言扩充（199→211→224 条），始终未被任何测试用例捕获；最终由真实用户案例（1987-05-06 06:30）触发。

**根因分层**：

| 层 | 根因 | 证据 |
|----|------|------|
| 直接层 | 断言集缺少「节气当天 + 节气前/后时刻」边界用例：224 条断言全部使用「非节气当天」或「节气后」日期，无一条覆盖「节气当天 00:00-节气时刻之间出生」 | 全量测评手册 §2.1「月柱排盘」仅标注「节气月判定 + 五虎遁口诀」，无节气边界专项；main.js 断言中无 monthPillar 边界单测；v0.22.0 小寒偏移修正（1/1-1/5 月柱丑→子）是唯一节气相关断言，但属「跨月数据修正」非「当天时刻边界」 |
| 机制层 | 测试用例设计以「功能正确性」为中心而非「边界时刻」为中心：排盘测试样例通常取整点/日常时刻（如 05:01、22:01），缺乏「节气时刻 ± 几小时」的构造意识；且 224 条断言以「结果比对」为主，没有「构造边界输入」的用例生成方法 | TEST 全量测评手册、v0.22.0 TEST 用例均未见节气当天用例 |
| 历史层 | 节气边界属于「低频 + 高破坏」场景：一年 12 个节令，单个用户恰好「节气当天出生且时刻在节气前」概率低（约 1-2%），但一旦触发直接崩溃且报错信息（getUTCFullYear null）远离根因，用户难以自助排查 | 本项目上线以来 v0.9.3 至 v0.23.3 共 15+ 版本，首次被真实用户触发 |

**影响评估**：单一崩溃点 + 完整错误链（月柱错→起运错→越界→崩溃），但触发概率低；本次修复为「根到梢三层封堵」，修复后节气当天边界全部按完整时刻判定。

**结论**：需要把「节气当天边界」纳入常规测试集（详见 §五 防再发机制 M1）。

### 问题 2：版本号漂移（v0.23.1 起草 vs 实际 v0.23.3+）⚠️

**事实链**：SYSTEM.md 停留在 v0.23.0，docs/ 已有 v0.23.1~v0.23.3 部署报告但 SYSTEM.md 未同步；新编排起草 PRD 时按「当前版本 v0.23.0 → PATCH v0.23.1」推理，与实际 git 历史（v0.23.3）冲突。

### 问题 3：v0.24.0 账号功能残留改动与本次发布基线混叠（已闭环）

**事实链**：运行目录 git 工作区存在 v0.24.0 账号功能的未提交改动（handler.rb 含 10 条 JS 路由、index.html 等），发布师采用**内测目录 = v0.23.3 干净基线 + 仅叠加修复 diff** 的发布方式，天然排除 v0.24.0 半成品。

**闭环结果**（RELEASE 确认）：内测 5 文件与 commit 177834f diff 0；端点验证 config.js 404（确认无 v0.24.0 泄漏）；公测 v0.24.0 未提交改动未触碰。**发布基线隔离策略有效，未造成混入事故**。正式发布（公测）时 handler.rb 含 v0.24.0 未提交改动，需 Leader 决策基线方案（详见 §六 R3）。

### 问题 4：编程师首版 commit 漏改 render.js（多文件同步类遗漏）⚠️

**事实链**：ADR 将「render.js 4 处 renYuanSiLing 调用改 5 参」列为关键实现待办并预警「最容易漏的一处」；编程师首版 commit（9fe5af3）实际只改了 algorithm.js/index.html/standalone.html/main.js 四文件，**render.js 4 处调用仍 3 参**（L1326/1331/1340/1348），同时四文件头部版本注释全部未更新。流程师/架构师/测试工程师三方交叉复核同时发现，Leader 汇总后一次性退回编程师补齐。

**根因**：
| 层 | 根因 | 证据 |
|----|------|------|
| 直接层 | 编程师修改算法签名（algorithm.js renYuanSiLing 3 参→5 参）时，只改了定义与内联版调用点，遗漏模块版 render.js 的 4 处调用——render.js 与 algorithm.js 分属两个文件，改动时「定义改了但调用没跟上」 | commit 9fe5af3 未含 render.js；render.js L1326/1331/1340/1348 仍 3 参 |
| 机制层 | 编程师自查依赖 ?test=1 断言（T01-T04 全绿），但断言走的是内联版（standalone/index 内嵌算法 + main.js），**不覆盖 render.js 模块版调用路径**——断言全绿 ≠ 模块版正确 | QA 确认 ?test=1 三入口全绿，但 render.js 调用遗漏未被断言捕获 |
| 历史层 | 「多文件同步」是本项目高频遗漏模式（v0.23.0 L1 同类：内联版与 render.js 漂移）；ADR 虽预警但实现阶段无强制检查点（check-release.sh 校验的是四文件一致性，不含 render.js 调用签名） | v0.23.0 复盘 L1、本次再次触发 |

**影响评估**：若未发现，模块版（standalone-split.html 走 render.js）人元司令时分参数丢失、退化为零点比较，与内联版行为不一致——功能错误（非崩溃）且无断言捕获，是最隐蔽的一类问题。本次被三方交叉复核及时拦截，未流出 QA 前。

**结论**：check-release.sh 应增加「render.js 调用签名与 algorithm.js 签名一致性」静态检查（详见 §五 M6）。

## 七、经验沉淀

- **节气边界测试方法论**：排盘类算法测试必须包含「规则切换时刻 ± 若干小时」的边界用例构造，不能只测日常时刻。本次教训可推广至日柱换日（23:00）、年柱换年（立春）等所有「时间分界」逻辑。
- **低频高破坏场景的测试策略**：触发概率低但后果严重（崩溃）的场景，应通过「构造边界输入」而非「等真实用户」来覆盖。
- **节气表 UTC 基准约定（编程师实测确认）**：SOLAR_TERMS 节气表与 sxtwl 对照确认存储为**真实 UTC**（getSolarTerm 返回真实 UTC epoch），monthPillar/paipan 用 +8h 转北京基准（BJT-as-UTC）自洽。**写期望值时注意不要拿 UTC 当北京时间**：如 2024 立春 UTC=02-04 16:26:53 = 北京时间 02-05 00:26:53，立春边界用例若按「02-04」写期望会错判。
