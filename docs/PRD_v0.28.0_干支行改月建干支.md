## 一、需求来源与目标

### 1.1 用户原话（需求来源）
- 「**切换成月建干支**」
- 前置背景：「**这个区主要是看所选年内的月建干支**」

### 1.2 目标区域
大运流年区**下方**的「当年节气数据」展示区（v0.26.0 引入的 12 节横排块，`.jieqi-section`）。

### 1.3 需求一句话
把每列**最后一行「干支」**的语义，从「**交节当天公历自然日的日柱**」切换为「**该节所起月份的月建干支（月柱）**」。

- ❌ 不改八字主盘（四柱区）的年/月/日/时柱显示与算法。
- ❌ 不新增列、不删列、不改横排与断点布局、不改 CSS 结构与类名。
- ❌ 不提交 git、不改 `ext.yml` 版本号、不改 CHANGELOG（留待发布阶段由发布师处理）。

## 四、口径与推导规格（核心）

### 4.1 展示语义（新）
每列第 6 行 `.jq-gz` = **该节所起月份（月建）的月柱干支**。
- 例：**立春**列 = 寅月之月柱；**惊蛰**列 = 卯月之月柱；……**小寒**列 = 丑月之月柱。
- 即：12 节 = 12 个「月建」（寅→丑），与该年干支年的十二月建一一对应。

### 4.2 取数口径（直推，**不**走出生时点比较链）
```
yearGan = yearPillar(year).gan        // year = 节气块注入的「所选年」（公历年）
i       = 列序 0..11（MONTH_TERM 顺序：寅=0 … 丑=11）
月支 zhi = DZ[(i + 2) % 12]           // 0→寅, 1→卯, … 11→丑
月干 gan = TG[(TG.indexOf(WU_HU_DUN[yearGan]) + i) % 10]   // 五虎遁起寅月，顺推
```
- 复用既有常量：`DZ` / `TG` / `WU_HU_DUN`（`constants.js:386/387/3164`，均已在 `render.js` 作用域可见）。
- 复用既有纯函数：`ALGO.yearPillar`（`algorithm.js:195`）。
- **与 `ALGO.monthPillar` 的关系**：本规格与 `monthPillar` 的「月支/月干」推导**同源同式**（`algorithm.js:203-243` 的 `zhi = DZ[(i+2)%12]`、`gan = TG[(indexOf(WU_HU_DUN[yearGan]) + i)%10]`），但**刻意剥离其基于出生时点的节气边界比较**——该比较链存在已知 8 小时偏移（§6.3），本需求不依赖、不触碰。

### 4.3 年基（重要，防 off-by-one）
- 五虎遁的**年基** = 节气块注入的 `year`（该年**立春**起的干支年），对**全部 12 列**一致，**包括末位小寒**。
- 末位**小寒**的节气表年份为 `year + 1`（公历落在次年 1 月，`buildJieqiHtml` 现有 `termYear` 逻辑），但它属于**干支年 `year` 的丑月**，故 `yearGan` 仍取 `yearPillar(year)`。
  - 反例警示（已在锚点复核中排除）：**不得**用 `yearPillar(year+1)` 推小寒列，否则 1982 年小寒会错成甲寅（正确应为**癸丑**）。

### 4.4 格式与结构（**零变化**）
- 输出仍为 `<div class="jq-gz"><span class="jq-gan">干</span><span class="jq-zhi">支</span></div>`（`.jq-gan` 在上 / `.jq-zhi` 在下，竖排；CSS 不动）。
- 插入位序 **硬约束不变**：`.jq-md → .jq-tm → .jq-tsmd → .jq-tstm → .jq-name → .jq-gz`（保 v0.26 T03 正则与 v0.27-T05 行序断言）。
- 每列**仍为 6 行**，12 节**仍横排**，`.jq-col` 的 `data-term` 属性不变。

### 4.5 边界与占位（沿用 v0.26 表外防御）
- `st === null`（表外越界，如 **2100 年小寒**）→ 该列 `.jq-gz` **保持占位** `<span class="jq-gan">—</span><span class="jq-zhi">—</span>`，与同列 `.jq-md/.jq-tm` 的「—」一致，**不抛异常**。
- 整块越界（`year < 1000 || year > 2101`）→ 沿用 `.jieqi-note` 占位提示，不变。
- 详见 §5.3 待裁决 D2（「null 时是否允许月建独立显示」）。

## 六、影响范围 / 风险 / 待裁决

### 6.1 影响范围
- **代码**：仅 1 个函数（`jqGanzhiOf`）+ 1 个调用点（`buildJieqiHtml` 内）+ 1 处注释，三端同步（§3 C1–C6）。

### 6.2 风险
| 风险 | 等级 | 缓解 |
|---|---|---|
| **年基 off-by-one**（小寒列误用 `year+1` 年干） | **高** | §4.3 明文；AC02 锚点含小寒 `癸丑` 直接锁定 |

### 6.3 「8 小时偏移」不在范围声明（Leader 口径）
`algorithm.js:203-243` 的 `monthPillar` 采用「节气表 `getTime()+288e5`」与「出生 `Date.UTC`」比较，二者时基存在已知 **8 小时偏移**问题。用户已明确**暂搁置**。
**本需求刻意改为五虎遁直推（§4.2），不进入该比较链**，因此：
- 本版**不修复**该缺陷；
- 该缺陷**不阻断**本版验收；
- 若要单独立项修复，须由 Leader 另行派单（不得由本 PRD 顺带处理）。

### 6.4 待裁决（请架构师在 ADR 中敲定）
- **D1｜函数签名方案**：`jqGanzhiOf(st)` → 改为 `jqGanzhiOf(st, yearGan, i)`，**或**新增纯函数 `jieqiMonthGZ(yearGan, i)` 并由 `jqGanzhiOf` 内调（保留 `st` 仅作 null 判定）。倾向后者（可测性更好、`st` 职责更纯）。请裁决并给出 `RENDER` 导出兼容策略。
