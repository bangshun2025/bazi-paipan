## 三、需求背景

**问题现象**：AI 录入「奕澄老公，男，1987年5月6日 6:30 北京时间」排盘失败，页面报错：

```
排盘出错：Cannot read properties of null (reading 'getUTCFullYear')
```

**根因摘要**（Leader 已确认，无需重新调查）：

1. 1987-05-06 恰逢**立夏节气当天**（立夏时刻约 17:05），出生 6:30 在立夏**前**，正确月柱应为**辰月**。
2. `monthPillar()` 判断月份时用**节气日期零点**（`new Date(st.getFullYear(), st.getMonth(), st.getDate())`）而非节气**完整时刻**，导致 `6:30 >= 立夏日零点(00:00)`，月柱错判为巳月（乙巳）。
3. 月柱错为巳月后，**逆排起运**找巳月节气立夏发现在未来，回退到 1986 年立夏 → 间隔 365.12 天 → 起运 **121 年 8 月**（正常约 10 年）。
4. 起运日期 2109 年 1 月，**超出节气表（1000-2100）**，渲染交运时 `getSolarTerm(2109, ...)` 返回 `null`，交运节气循环（standalone.html ~7204/7210 行）**无判空**直接 `.getUTCFullYear()` → 崩溃。

**使用场景**：任何**出生在节气当天且时刻在节气前**的用户排盘（立夏/立秋/立冬/立春等 12 个节令边界日），以及**起运日期越出 2100 年**的极端排盘，均可能触发。

## 四、方案概述

### 4.1 总体思路

三处修复，从根到梢逐层封堵：

| 修复 | 位置 | 内容 |
|------|------|------|
| ① | `monthPillar()`（algorithm.js ~203 行；standalone.html / index.html 内联版） | 节气区间判断改用**节气完整时刻**（保留时分），不再截断为日期零点 |
| ② | `renYuanSiLing()`（algorithm.js ~555 行；standalone.html / index.html 内联版） | 同样的零点比较问题（节气当天出生显示「立夏后 0 日」），一并改为完整时刻比较 |
| ③ | 交运节气循环（standalone.html ~7204/7210 行、index.html ~7206/7213 行；render.js 375/381 行已有判空） | 补 null 防护：`getSolarTerm` 返回 null 时用哨兵日期（`new Date(-8640000000000000)` / `new Date(8640000000000000)`），防止 2101+ 越界崩溃 |

### 4.2 技术方案决策点（架构师 ADR 细化）

**决策 1：monthPillar 节气区间比较基准。** 候选：

| 方案 | 描述 | 优劣 | 倾向 |
|------|------|------|------|
| A. 直接用节气完整时刻比较 | `birth >= st && birth < nextSt`（st/nextSt 为 `getSolarTerm` 返回的完整 Date，含时分） | 最准确；改动最小（删掉零点截断一行）；与 renYuanSiLing 共用同一基准 | ✅ **推荐** |
| B. 截断到分钟后再比较 | 对 st 做 `setSeconds(0,0)` 再比较 | 能解决「同日同刻」极边界的秒级误差，但节气表精度本身到分钟级，无实际收益 | ❌ 不推荐 |
| C. 保留零点 + 特判节气当天 | 仅对节气当天出生做时刻特判 | 逻辑分散，易漏其他边界日 | ❌ 不推荐 |

**倾向**：方案 A。理由：改动最小、语义最直白、与日柱/时柱的 `birth` 基准（本地时间）一致。注意 `getSolarTerm` 返回的是「BJT as UTC」Date（内部减 8h），比较时需与 `birth`（本地时间 Date）统一时区基准，具体实现细节由架构师在 ADR 确认（推荐统一用本地时间比较，或统一转 UTC 毫秒比较）。

**决策 2：交运循环 null 防护的哨兵值。** 沿用 render.js 既有写法（`new Date(-8640000000000000)` 作为「最早时刻」、`new Date(8640000000000000)` 作为「最晚时刻」），保持四文件写法一致，不做新发明。

### 4.3 修复后预期行为（以 1987-05-06 06:30 为例）

- 月柱：**甲辰**（辰月，丁卯年五虎遁丁壬起壬寅 → 寅壬寅、卯癸卯、辰甲辰）✅
- 人元司令：显示「谷雨后 N 日」（6:30 在立夏 17:05 前，属辰月，辰月司令从谷雨起算），不再出现「立夏后 0 日」
- 起运：阴年男逆排，约 **10 年**量级（正常值，非 121 年 8 月）
- 交运：起运日期落在 1997 年前后（节气表范围内），正常渲染，**不崩溃**

## 五、需求详述

### 5.1 修复① monthPillar 节气区间判断用完整时刻

**现状**（algorithm.js ~203-235 行）：

```js
const stDate = st ? new Date(st.getFullYear(), st.getMonth(), st.getDate()) : new Date(-8640000000000000);
...
const nextDate = nextSt ? new Date(nextSt.getFullYear(), nextSt.getMonth(), nextSt.getDate()) : new Date(8640000000000000);
if (birth >= stDate && birth < nextDate) { ... }
```

**改为**：

```js
// 直接用节气完整时刻比较，不再截断为日期零点
const stDate = st || new Date(-8640000000000000);
...
const nextDate = nextSt || new Date(8640000000000000);
if (birth >= stDate && birth < nextDate) { ... }
```

**要求**：
- 保留原有 `beforeLC`（立春前判断，用于大雪/小寒年份选择）逻辑不动——它只影响年份选择，不参与本次时刻精度问题；但若该处同样存在零点截断影响「立春当天」边界，架构师需一并评估（见 §9.2）。
- null 哨兵逻辑保留（`st ? ... : 哨兵` 与 `st || 哨兵` 等价，实施时可保持原三元写法只改日期构造部分，最小 diff）。

### 5.2 修复② renYuanSiLing 同样改完整时刻

**现状**（algorithm.js ~555-585 行）：

```js
const stDate = st ? new Date(st.getUTCFullYear(), st.getUTCMonth(), st.getUTCDate()) : new Date(-8640000000000000);
...
const nextDate = nextSt ? new Date(nextSt.getUTCFullYear(), nextSt.getUTCMonth(), nextSt.getUTCDate()) : new Date(8640000000000000);
if (birth >= stDate && birth < nextDate) {
  const daysAfter = Math.floor((birth - stDate) / 86400000);
  ...
}
```

**改为**：与修复①相同的完整时刻比较；`daysAfter` 天数计算以完整时刻为基准（节气当天且时刻在节气前 → 属于上一月，daysAfter 为上一节气的天数，不出现「0 日」）。

### 5.3 修复③ 交运节气循环补 null 防护

**现状**（standalone.html ~7204/7210 行、index.html ~7206/7213 行）：

```js
const stDate = new Date(st.getUTCFullYear(), st.getUTCMonth(), st.getUTCDate());   // st 可能为 null → 崩溃
...
const nextDate = new Date(nextSt.getUTCFullYear(), nextSt.getUTCMonth(), nextSt.getUTCDate());  // nextSt 可能为 null → 崩溃
```

**改为**（与 render.js 375/381 行现有写法对齐）：

```js
const stDate = st ? new Date(st.getUTCFullYear(), st.getUTCMonth(), st.getUTCDate()) : new Date(-8640000000000000);
...
const nextDate = nextSt ? new Date(nextSt.getUTCFullYear(), nextSt.getUTCMonth(), nextSt.getUTCDate()) : new Date(8640000000000000);
```

**注意**：render.js 已有此判空，**不要改坏**；本修复的目标是让两个内联版与 render.js 对齐（L1 规避）。

## 九、风险评估

### 9.1 时区基准不一致

**风险**：`getSolarTerm` 返回「BJT as UTC」Date（内部减 8h），而 `birth` 是本地时间 Date。若修复①直接用 `birth >= st` 比较，在**非 UTC+8 时区**（如浏览器本地时区为 UTC）可能出现偏移。

**缓解**：PRD §4.2 已要求架构师在 ADR 明确统一比较基准（推荐统一转 UTC 毫秒比较，或统一用本地时间构造）；测试在本地（UTC+8）与 UTC 环境各跑一遍边界用例（AC06）。

### 9.2 beforeLC 立春边界潜在同类问题

**风险**：monthPillar 中 `lcDate = lc ? new Date(lc.getFullYear(), lc.getMonth(), lc.getDate()) : null` 同样是日期零点截断——立春**当天**且时刻在立春前出生的用户（如 2 月 4 日凌晨），可能同样被误判「立春已过」而选错大雪/小寒年份。

**缓解**：架构师在 ADR 中评估是否将 `beforeLC` 一并改为完整时刻比较（本 PRD 建议顺带修复，最小 diff；若评估确认不涉及，需在 ADR 写明理由）。验收用例补一条：立春当天凌晨出生（如 1987-02-04 02:00）排盘不崩溃且月柱正确。

### 9.3 内联版同步遗漏（L1 复发）

**风险**：只改 algorithm.js/render.js 而漏同步 standalone.html/index.html，模块版正常、内联版仍崩溃——本次 bug 的原始成因。

**缓解**：PRD §5.4 列为硬性门槛；AR04/AR05 双环境三入口验证；check-release.sh 六模块一致性检查（编程师确认覆盖本次改动段）。

### 9.4 人元司令 daysAfter 语义
